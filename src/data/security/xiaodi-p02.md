## 1. 回顾：常规站 vs 站库分离（00:00-02:41）

| 架构 | 特点 | 拿到 webshell 后 |
|---|---|---|
| 常规搭建 | 源码+数据库同一台服务器 | 后门传到源码目录，连的就是本机，本机有库 → 可直接脱库 |
| 站库分离 | 库在另一台服务器/云数据库 RDS（单独买产品，不用买服务器） | web 权限 ≠ 数据权限，连不上库就碰不到数据 |

⚔️ **安全思维**：这是后面所有架构对比的"母题"——**权限是分层隔离的**。渗透目标不能只盯着"进没进站"，要问自己：这个权限能不能摸到数据？缺哪条链路（数据库连接串、内网可达性）？

## 2. 前后端分离站（02:41-13:16）★本集难点

**原理**（02:41-06:39）：前端 = 你看到的界面，用 **JS 框架**（Vue/React）写；后端 = 单独一套管理后台，**可能在另一个域名甚至另一台服务器**。两边是两个独立"网站"，靠 **API 接口**传数据：后台改数据 → API 推给前台显示。老师演示了一个基于 Vue 的产品站：后台不在主站目录下，而是挂在**单独域名**上。

**三点安全影响**（06:39-12:00）：
1. **前端几乎无漏洞**：HTML/JS 是前端语言（纯展示），PHP/JSP/Java/.NET 是后端语言（有逻辑）。Vue/React 这类知名框架本身很少出洞，页面"光秃秃"，数据全走 API，没有传统代码逻辑漏洞。
2. **目录扫描失效**：后台在别的域名，按常规思路扫主站目录找后台=白扫，信息收集不到就是没有。
3. **拿下前台 ≈ 拿了个寂寞**：前台上传 webshell 也**不影响后端**——除非后台是主域的子域（如 `admin.xxx.cn`，同域可能波及），否则一个在东一个在北，互不相干。

**渗透思路**（11:58-12:49）：① 找到后端地址 → 测后端（后端才是后端语言写的）；② 找不到 → 测前端框架历史漏洞；③ 还没有 → 只能从社工、旁站等其他应用点入手。

**怎么识别**（12:50-13:16）：看页面简洁程度——极简、美观、没多余分类栏目，大概率是前后端分离（后面信息收集课会讲系统判定方法）。

⚔️ **安全思维**：架构即防御。这类站从设计上就抬高了攻击成本，安全测试前先做**架构指纹识别**，别把"扫不到后台"当成"没有后台"。

## 3. 集成软件站：宝塔 / phpStudy / IIS 三方对比（13:17-46:13）★本集最重头

**为什么有集成环境**（13:17-15:00）：P1 那种一个一个装中间件、数据库、语言的方式复杂且重复，于是有了打包好的集成环境——早年 phpStudy，现在主流是宝塔（主要搭 PHP 站，Java/Python 也能搭但少）。

**演示全流程**（15:01-27:42）：
- 买阿里云按量付费服务器（香港节点，因为域名没备案；2核4G，0.373 元/小时+流量费）→ **17:17-17:39 安全组全端口放行**（否则访问被云防火墙拦）；**18:04-18:28**：25 端口（发邮件用）默认强制关闭，要提工单申请——云厂商防钓鱼邮件滥用。
- 服务器里装宝塔 Windows 版 → 登面板 → 软件商店一键装 **Apache + MySQL + PHP** 三件套（23:24-24:22，中间件/数据库/语言同时装）→ **一键部署** Zblog 源码 → 绑域名 → 去解析控制台把 A 记录指向服务器 IP → 源码自动下载、账号密码自动生成，网站直接能用（24:24-27:42）。

**攻击者视角对比实验**（27:44-46:13）——老师生成后门上传，用 webshell 管理工具连接：

| 搭建方式 | 文件管理 | 命令执行 | whoami 返回 |
|---|---|---|---|
| 宝塔（28:10-31:30） | 锁定在网站目录，上级目录提示"路径没有发现或没有权限"，看不到 C 盘 | **被禁用**，报函数禁用错误 | 无 |
| phpStudy（35:14-38:29） | 不受限 | **能执行** | 主机名+**administrator**（38:29-38:43） |
| 自装 IIS（39:07-42:20） | 能看到上级目录（比宝塔强），C 盘受限 | 部分能执行部分不能（42:07-42:19） | 返回身份和前两者都不同（应用程序池身份） |

> 细节：装 phpStudy 前要停掉宝塔，**80 端口冲突**（35:32-36:50，两个中间件抢同一端口——你数通里"端口唯一占用"的直觉在这直接适用）；IIS 默认不支持 PHP，所以生成的是 **ASP** 后门，且老师强调：差异与脚本语言无关，是**搭建方式**造成的（40:28）。

**原因分析**（42:20-46:13）：
- **权限继承**（44:41-45:24）：phpStudy 是系统之外的第三方软件，你用什么权限装它，它就继承什么权限——管理员装的，它启动的 Apache 就带着管理员权限跑，webshell 自然也是 administrator。
- **宝塔的安全内核**（43:17-43:46）：用户多了之后官方在核心里加了防护（防跨目录、禁危险函数、防文件被删），所以最安全。
- **phpStudy 也有安全设置**（44:08-44:36）：建站时有"安全设置"选项，但**默认全部关闭**。

⚔️ **安全思维**：**"环境=权限边界"**——同样一个 webshell，宝塔站只给你网站目录只读，phpStudy 站直接是 administrator。实战里拿到 webshell 的第一件事就是 `whoami` 看运行身份，判断下一步是直接横向还是先想办法提权/跨目录；防御方同理：中间件跑在低权限账户+禁用危险函数，webshell 的破坏力就砍掉一大半。

## 4. Docker 容器站（46:13-58:45）

**是什么**（46:13-47:54）：一种虚拟化技术（类似虚拟机但更轻），18、19 年在国内火起来。别人把"网站+环境"封装成**镜像**，你从 **Docker Hub**（hub.docker.com）拉下来直接跑，一行命令完成建站。老师还提到 vulhub 这类漏洞复现镜像库，以后做靶场常用。老师明确说：**不是学运维，是让你碰到这种站知道怎么回事**（48:19-48:28）。

**演示**（48:30-52:13）：Docker Hub 搜 Tomcat → 选 8.0 → 复制命令：

```bash
docker pull tomcat:8.0        # 拉取镜像
docker run -p 8080:8080 镜像名  # 启动并把容器8080映射到宿主机8080
```

浏览器访问本地 8080 → Tomcat 起来了，就这么简单。

**关键实验：容器里的"假象"**（53:37-58:45）：老师模拟利用 Tomcat 漏洞（过程不用深究）把后门放进容器站，连上 webshell 后：
- 老师做了什么 → `whoami` 返回 **root**，`ls` 什么都能看，看起来权限拉满；
- 现象 → 他在**宿主机**根目录新建 `1.txt`，webshell 里刷新根本看不到；进 `/home` 也是空的，IP 还是 172 网段的容器内网地址，和服务器真实 IP 对不上；
- 道理 → 你拿到的是**容器这个虚拟空间的 root，不是宿主机权限**，一直在"小房间"里玩。想从虚拟空间逃到真实服务器，就叫 **Docker 逃逸**（57:57-58:24，后续课程讲）。

⚔️ **安全思维**：实战遇到 Docker 站，`whoami=root` 别高兴太早——先判断是不是容器（查 `/.dockerenv`、看 IP 是不是 172.17 网段、`ls /` 特征），权限评估直接降一档；反之防御方用容器隔离业务，本来就是一道边界。

## 5. 建站分配：托管站 vs 申请站（59:00-69:20）

**两类情况**（59:48-60:20）：① **托管**：单位把网站外包给别人做（常见于政府/企业门户），但备案、注册信息都是真实的；② **申请**：在建站平台白嫖模板自己改。

**演示**（60:21-63:54）：老师注册凡科建站 → 平台自动分配一个域名 → 选模板、改内容为"小迪安全" → 有后台能加产品。关键点：**域名是平台的**，自定义前缀要花钱且主域名改不了。

**安全测试的意义**（63:55-69:20）：这种站你以为测的是"某某公司"，实际**测的全是建站平台**——打的是平台，跟站长半毛钱关系没有（64:55-64:58，老师原话式举例：明天我把我博客也搬上去，你打吧）。这类站上不会有核心数据，服务器、域名、源码都不是站长的。

**怎么识别**（65:21-68:54）：做信息收集时**查域名备案/whois**——备案公司是"凡科建站"而页面自称某公司 → 对不上 → 建站平台申请的；对得上 → 可能是托管外包站，此时你面对的实际是外包公司的安全实力。

⚔️ **安全思维**：**资产识别是渗透第一步**。收集目标资产时碰到"分站"，先用备案信息验明正身，别把平台的站当成客户目标——既浪费弹药又可能越权打到无关方。

## 6. 答疑补充：前后端分离的取舍（69:21-74:06）

- 用 SpringBoot+Vue 的开源项目举例：前端一套负责显示、后端一套负责处理；常规源码则显示和处理在一起——这就是技术成因。
- 架构一变，**漏洞出现的位置也变**：常规漏洞要么不出现、要么换个地方（71:17-71:24）。
- 并非所有站都是前后端分离，老牌网站大多还是常规架构。
- 优劣对比（71:54-72:51）：优点是开发快、安全；缺点是 **API 传输大数据时效率不如传统方式** → 安全和效率不可兼得，按业务场景选。
- 更宏观的结论（73:14-74:05）：网站选什么产品从第一天起就决定了安全下限——ASP 时代最不安全，现在 PHP 稍好，Java 更好；"有些非专业的人搭的站反而安全"，纯粹因为选对了产品。

## 7. 静态网站与伪静态（74:18-96:30）

| 类型 | 特征 | 内容怎么改 | 安全性 |
|---|---|---|---|
| 纯静态 | 单页/几个简单页面，无导航无分栏（如传奇私服单页站） | 只能改代码再覆盖，没后台 | **基本无漏洞**——数据没有传输性；但 HTML 里嵌 JS（AJAX）传数据就有洞（79:44-80:29） |
| 动态 | 有后台有数据库 | 后台点几下 | 传统漏洞面 |
| **伪静态** | 动态站伪装成静态 | 后台改，页面呈现为 .htm | 看着像静态其实是动态 |

- 识别技巧（76:23-76:48）：看美工复杂程度——界面缭乱、光秃秃单页面 → 多半静态；有文章列表能翻页的"静态"其实是伪静态（77:00-78:30，直播间某兄弟发的站就是伪装静态的动态站）。
- 静态和前后端分离也不是绝对的，静态页一样可以用 JS 传数据（78:39-79:00）。
- **插曲**（83:00-92:55）：直播中有人把老师的 Zblog 后台密码改了。老师现场应急：进数据库 → 发现 Zblog 密码**不是 MD5**，是另一种加密密文 → 查清加密格式后把密文替换成已知明文（123456789）对应的密文 → 恢复登录。顺带演示了 Zblog 的静态化插件（93:00-96:30，部分插件收费）：发布文章时可把页面生成 HTML 缓存，即伪静态。

⚔️ **安全思维**：改密码插曲就是一次完整的**账号接管+应急恢复**：密码丢失走数据库密文替换是运维常用手段，前提是你知道加密算法——反过来这也提醒站长：数据库一旦被打穿，密码重置形同虚设（哈希不可逆，但密文可替换）。

## 8. 彩蛋实战：access 日志溯源抓"内鬼"（96:40-99:44）

密码被改了，怎么揪出人？老师的思路：

1. 到网站 `logs` 目录下载 **access 访问日志**（就 200 多行）；
2. 先排除自己的 IP（171 结尾的是自己）；
3. **结合业务逻辑定位关键页面**：改密码必然要访问后台地址（`zb_system`）和用户管理页 → 在日志里筛"访问过这些地址"的记录；
4. 反查命中记录的来源 IP → 锁定 `58.x.x.x`（上海）——就是直播间改密码的内鬼。

⚔️ **安全思维**：这是最朴素的**日志审计溯源**：攻击路径 = 业务逻辑 × 日志记录。防守时保证日志完整、可回溯，入侵发生时就能从"发生了什么"倒推"谁干的"；攻击者视角则要记住——你踩过的每个 URL 都会留在对方日志里。
